## 4. 技术方案

### 4.1 场景配置系统（REQ-17 / REQ-20）

**现状**：场景写在 `backend/app/services/prompts/materials.json`（单场景 + 三档 level 的 opening/follow_ups/practice_sentences），开场白在 session_svc 内固定。

**方案**：

1. 新增场景配置目录 `backend/app/services/prompts/scenarios/`，每个场景一个 JSON 文件，内容对应 PRD 9.1 ScenarioPack 字段：

   ```
   {
     "scene_id": "job_interview",
     "series": "career",                    // 职场与求职
     "version": "v1",
     "review_status": "approved",           // draft / approved / retired
     "levels": ["beginner", "basic", "intermediate"],
     "user_role": "求职者",
     "coach_role": "面试官",
     "goal": "介绍一段经历并回答相关追问",
     "openings": { "beginner": "...", "basic": "...", "intermediate": "..." },
     "follow_up_strategy": "...",           // 追问必须引用用户真实信息
     "acceptable_points": ["..."],          // 可接受回答要点
     "help_materials": "...",               // 帮助材料
     "reference_expressions": ["..."],      // 参考表达
     "variations": ["..."],                 // 常见变化
     "stop_conditions": "...",              // 停止条件
     "completion_criteria": { "independent": "...", "assisted": "...", "incomplete": "..." }
   }
   ```

2. 新增 `ScenarioPack` 数据表（见第 5 节）记录场景元数据与审核版本，作为「只读已审核版本」的依据。
3. 会话创建时绑定 `scene_id + scene_version`，开场问题与完成条件从配置读取，不再硬编码在 session_svc。
4. **完成条件随场景变化**：酒店入住关注信息确认、会议表达关注观点与理由、日常社交关注能否自然延续对话；不共用英文面试的评价标准（对应 AC07-18）。

### 4.2 七个场景内容（REQ-20）

| 系列 | scene_id | 场景 | 本次小目标 | 发布范围 |
| --- | --- | --- | --- | --- |
| 职场与求职 | job_interview | 英文面试 | 介绍一段经历并回答相关追问 | 已有场景改造 |
| 职场与求职 | new_colleague | 认识新同事 | 完成自我介绍并向对方提出一个问题 | P0 |
| 职场与求职 | meeting_opinion | 会议中表达意见 | 清楚说明观点并回应一次追问 | P0 |
| 旅行与生活 | hotel_checkin | 酒店入住 | 确认预订并询问一项服务信息 | P0 |
| 旅行与生活 | restaurant_order | 餐厅点餐 | 完成点餐并处理一个补充问题 | P0 |
| 日常交流 | new_friend | 认识新朋友 | 介绍自己并延续两轮简单交流 | P0 |
| 日常交流 | hobby | 聊兴趣爱好 | 描述一项兴趣并说明喜欢的原因 | P0 |

每个新增场景先过固定测试集 + 人工审核，再进真实用户练习。本 P0 不增加第八个场景。

### 4.3 设备预检（REQ-19）

- 前端在首次语音练习前执行预检：麦克风权限、录音输入、音频播放、网络连通，每项给出可理解状态与修复动作。
- 预检失败仍可进入文字练习，页面明确说明「文字回答不参与发音评价」。
- 后端新增 `DeviceCheck` 记录（仅设备摘要 + 检查状态 + 时间，**不保存测试音频、不采集硬件序列号**）。
- 更换浏览器/麦克风，或连续两次录音失败时，触发重新检查。

### 4.4 会话恢复 + 服务端时长确定性收尾（REQ-26 / REQ-07 / REQ-14）

- **服务端计时**：以 `started_at + duration_minutes` 为界，服务端判断到时；到时后停止开启新问题，允许当前提交在限定时间内完成，然后进入收尾。不能只靠前端显示计时。
- **刷新 / 断网恢复**：前端从服务端读取会话状态、最后完整回合、处理中请求状态；结果已保存的只恢复展示，不重复调用模型、不重复计费；处理超时的恢复到可重试状态并说明已保存内容。
- **幂等保护**：结束、删除、暂停、继续、帮助、练习提交全部幂等。
- **迟到响应拦截**：会话进入结束态后，迟到响应不得新增回合、播放音频、恢复录音。

## 5. 数据模型变更

| 实体 | 变更 | 关键字段 |
| --- | --- | --- |
| ScenarioPack | 新增 | scene_id、series、version、review_status、content_json、published_at |
| Session | 扩展 | 新增 scene_id、scene_version；subgoals 复用 |
| DeviceCheck | 新增 | user_id、device_summary、status、created_at（不含测试音频） |

所有派生数据保留来源标识与计算版本；源文本修订或删除时派生数据可定位并失效（沿用 v0.6 数据边界）。

## 6. 接口设计

| 接口 | 说明 |
| --- | --- |
| `GET /api/v1/scenarios` | 已审核场景列表（series + scene 概览） |
| `GET /api/v1/scenarios/{scene_id}` | 场景详情（角色、目标、预计时长、难度、开口示例） |
| `POST /api/v1/sessions` | 创建会话，新增 scene_id 入参，校验已审核版本 |
| `POST /api/v1/device-check` | 记录设备检查结果摘要（不含音频） |
| 会话恢复 | 复用现有会话状态接口，扩展处理中状态与幂等键 |

统一错误结构、SSE 以 done/error 收尾、进步指标后端计算等原则继续沿用。

## 8. 风险与边界

- **场景内容质量**：配置版本化 + 固定测试集 + 人工审核 + 小流量开放，避免内容质量下降。
- **范围控制**：P0 不新增第八个场景；待复练队列、进步中心、词级发音证据归 P1。
- **真实与 Mock 区分**：Mock 回归通过不能替代真实教学 / 语音 / 时延 / 费用验证；真实环境复验单独记录。
- **不触碰**：不修改 v0.6 已实现且不影响 P0 的功能、测试、用户数据。
